# S3 Tables 重複排除の検討

作成日: 2026-10-28

## 1. 要点

- **課題**: Kafka → Lambda（ESM）→ S3 Tables の経路で、同じメッセージ（`DeviceId + MessageID`）が重複して登録されるのを防ぎたい。
- **難しさ**: 重複キーは圧縮 payload の中にあり、producer は変更できず、キーでテーブルの partition も切らない。Iceberg には一意制約がない。そのため、重複の判定は Lambda 以降のどこかで自前で行う必要がある。
- **すべての重複を、即時に、窓の制約なく落とせる案はない**。「遅れて届いた重複をどこまで落とすか」「重複が一時的にテーブルに見えてよいか」「本テーブルへの反映が遅れてよいか」のどれかで妥協が要る。
- **現時点の推奨**: Parquet 出力 + 短い間隔の定期 MERGE。Lambda は加工した行を Parquet に書くだけにし、1 本だけ動かす MERGE ジョブが 1〜5 分ごとに本テーブルへ反映する。本テーブルに重複が入らず、Lambda の commit もなくなる。代わりに、反映が MERGE の間隔だけ遅れる（9 章）。
- **Lambda が呼び出しごとに commit する構成の問題**: 基準ケースの流量では毎秒 5 回の commit になり、metadata の肥大化と commit の競合で成り立たない見込み（4.1 節）。追記 + 定期重複排除ジョブや、書き込み前に判定する案（DynamoDB、Valkey など）は、この構成を前提にしている。
- **照合範囲**: キーでテーブルの partition を切らなくても、同じメッセージのコピーが必ずテーブルの同じ partition に入るなら（同一テーブル partition 条件）、照合をそのテーブル partition に限定できる。テーブル側で照合する案の費用は、保持期間に依存しなくなる（2.6 節）。
- **未決事項**: 遅延上限、重複が見えてよい時間、再送でテーブル partition の元になる値が変わらないか、など（2.3 節）。

## 2. 前提

### 2.1 処理の流れ

```
デバイス（約 300 万台）
  → producer（変更不可）
  → Kafka（EKS 上）
  → Lambda（ESM でバッチ受信。以下はすべて Lambda 内の処理）
       1. zlib 解凍
       2. protobuf デコード
       3. 加工（1 メッセージ → N 行）
       4. PyIceberg で、バッチ内の全メッセージ分の行をまとめて append
  → S3 Tables（Iceberg）
```

### 2.2 確定した条件

- **重複キー**は `DeviceId + MessageID`。圧縮 payload の中にあり、protobuf のデコード後にしか取り出せない。
- **重複の単位はメッセージ**。1 メッセージから展開した N 行は、同じ重複キーを共有する。行は `DeviceId` と `MessageID` を列として持つ。
- **行は登録日時の列を持つ**。Lambda が書き込み時に付け、1 メッセージの N 行（またはバッチの全行）で同じ値にする。同じメッセージの別のコピーは別の登録日時を持つので、書き込み ID（2.4 節）の役目を果たす。行ごとの値にする場合は、行識別子も要る（5.3 節）。
- **加工は決定的**。同じメッセージを 2 回加工すると、行数と各行の値が毎回同じになる。
- **`MessageID` は連番ではない**（UUID などの非連番）。
- **同じデバイスのメッセージが、同じ Kafka の partition に入るとは限らない**。
- **`DeviceId` と `MessageID` はテーブルの partition に使わない**。
- **流量は秒間 300 万件未満**の想定（具体値は未定）。
- **原本（圧縮バイト）の保持と再処理の要件はない**。
- **加工を Lambda に残すことは必須ではない**。
- リポジトリ内のテーブルやコードはサンプルであり、本番の処理は別に作る。

### 2.3 未決の条件

- **遅延上限**（再送がどれだけ遅れて届くか）: 不明。窓を持つ案は、窓を超えた重複が漏れることを受け入れる前提で評価する。
- **重複が本テーブルに一時的に見えてよいか、その時間**: 未定。
- **本テーブルへの反映の遅れをどこまで許容するか**: 未定。推奨構成の MERGE の間隔を決める。
- **再送が元から何件以内に届くか**: 不明。直近 K 件リングの K の決定に必要。
- **再送で、テーブル partition の元になる値が変わらないか**: 未確認。同一テーブル partition 条件（2.4 節）に関係する。payload 全体が同一である必要はない。
- **Flink で加工を処理しきれるか**: 懸念があり、未検証。
- **実際の流量、行サイズ**: Firehose の上限や費用の判断に必要。リージョンは東京（ap-northeast-1）を前提にする。
- **producer で idempotence が有効か**: 変更はできないが、有効かどうかは確認できる。

### 2.4 用語

| 用語 | 意味 |
|---|---|
| `message_key` | `DeviceId + MessageID`。重複判定のキー。テーブルには `DeviceId` と `MessageID` の列として持つ |
| 書き込み ID | Lambda が 1 回の書き込み（1 バッチ）ごとに付ける識別子。そのバッチで書く全行に同じ値を入れる。同じメッセージの別のコピーは別の書き込み ID を持つので、テーブルに入った後でも、どの行がどのコピーに属するかを区別できる。登録日時の列（2.2 節）で代用できる |
| 行識別子 | 1 メッセージ内の N 行を区別する値。行番号（`row_index`）か、行に既にある区別できる列。`DeviceId + MessageID` と組み合わせて 1 行に決まり、どのコピーでも同じ値になる必要がある（加工で決まる行の順番や、行ごとの計測時刻など、payload から決定的に決まる値）。Lambda が行ごとに作る UUID や処理時刻は、コピーごとに値が変わるので使えない。unique keys で upsert する案と、登録日時を行ごとに入れて後から消す場合に必要 |
| 窓 | 重複を検知できる範囲。時間（TTL）か件数（K）で決まる。窓を超えて遅れて届いた重複は検知できない |
| TTL | Time To Live。状態ストアに保存したキーを自動で消すまでの時間 |
| K | 直近 K 件リングで、デバイスごとに覚えておく直近の `MessageID` の件数 |
| 座標 | Kafka の `(topic, partition, offset)`。レコードの位置を一意に示す |
| 状態ストア | 処理済みのキーを覚えておく外部ストア（DynamoDB、Valkey など） |
| snapshot | Iceberg のテーブルの、ある commit 時点の状態（データファイルの一覧）。append、削除、コンパクションなど commit のたびに 1 つ増える。snapshot ID（64 ビットの整数、連番ではない）、親の snapshot ID、commit 時刻、操作の種類、追加したファイルの一覧を持ち、書き込む側のライブラリが自動で作る。行には snapshot ID の列はない。古い snapshot は S3 Tables の snapshot の管理で消える |
| テーブルの partition | S3 Tables（Iceberg）のテーブルの partition。計測日などの partition 列で分ける。この文書では修飾なしの「partition」は使わず、Kafka の partition と書き分ける（「partition 列」はテーブルの partition 列を指す） |
| Kafka の partition | Kafka の topic の partition。ESM は Kafka の partition ごとに Lambda を起動する |
| 同一テーブル partition 条件 | 同じメッセージのコピーが、必ずテーブルの同じ partition に入ること。次の 2 つで成り立つ。(1) テーブルの partition 列を、payload の中の、メッセージの生成時に決まる値（計測時刻など）から作る。取り込み時刻、Kafka レコードの timestamp、Lambda の処理時刻は使わない（再送されたコピーは届いた時点の値になる）。(2) デバイスが再送しても、その値が変わらない。payload 全体が同一である必要はない。種別 1・2 はレコードの中身が同じで加工も決定的なので、(1) だけで成り立つ。種別 3 は (2) の確認が必要。成り立てば、照合をテーブル partition の中に限定できる（2.6 節）。Firehose の upsert のように、成り立たないと機能しない案もある |

### 2.5 行を区別する情報

`DeviceId + MessageID` だけで足りるかは、案によって違う。

- **書き込み前に判定する案**（バッチ内重複排除、DynamoDB、Valkey、直近 K 件リング、共有 Bloom filter、Kafka 内での重複排除）: メッセージ単位で判定するので、`DeviceId + MessageID` だけで足りる。
- **テーブルに入った重複を後から消す案**（追記 + 定期重複排除ジョブ、staging + 定期 MERGE、読み取り時の重複排除）: 同じメッセージが 2 回入ると、同じ `DeviceId + MessageID` の行が 2N 行になる。どの N 行が同じコピーかを区別するために、書き込み ID の列（登録日時で代用できる）を使う。
- **unique keys で upsert する案**（Firehose、Flink の upsert、PyIceberg の `upsert()`）: unique keys は 1 行を一意に識別する前提である。`DeviceId + MessageID` だけでは 1 メッセージの N 行が同じキーになり、upsert の意味では 1 行しか残らない（PyIceberg では入力の重複としてエラーになる）。行識別子を unique keys に加える必要がある。

後から消す案で、行番号ではなく書き込み ID を使う理由:

- **コピーを丸ごと残せる**。行番号で 1 行ずつ残すと、再送の payload が元と違う場合に、別々のコピーの行が混ざる。
- **Athena の `DELETE` で消せる**。行番号だけだと、2 つのコピーの行は全列が同じ値になり、列の値を条件にした `DELETE` では片方だけを消せない。書き込み ID が違えば、残さない側だけを条件で指定できる。
- **種別 1 の重複も区別できる**。再配信されたレコードは Kafka の座標が同じだが、書き込み ID は書き込みのたびに変わる。

前提として、バッチ内重複排除で、1 回の書き込みに同じメッセージのコピーが 2 つ入らないようにしておく。同じ書き込み ID の中では、コピーを区別できないためである。

### 2.6 テーブル partition で照合範囲を絞る

テーブル側で重複を照合する案（追記 + 定期重複排除ジョブ、MERGE 系の案など）は、照合の条件にテーブルの partition 列を加えられる（partition 列 + `DeviceId` + `MessageID`）。同一テーブル partition 条件が成り立てば、本テーブルから読む範囲は今回書き込みのあったテーブル partition だけになり、保持期間に比例しなくなる。この文書では、これを「テーブル partition 限定」、テーブル全体と照合することを「全体照合」と呼ぶ。

例: 5 分ごとに MERGE する場合、1 回に読むキー列は、時間単位のテーブル partition 限定なら平均 約 2.7GB（Athena で月 約 160 ドル）で済む。テーブル全体と照合すると、1 か月保持で約 3.9TB（月 約 17 万ドル）、12 か月保持で約 46.7TB（月 約 200 万ドル）になる。

- **条件が崩れた場合**: そのコピーは別のテーブル partition に入り、照合されない。重複は漏れるが、データは欠落しない。
- **テーブル partition の中は全行を読む**: キーでテーブルの partition を切らないので、対象のテーブル partition のキー列はすべて読む。sort order（7 章）によるファイル単位の絞り込みは、sort compaction 後のファイルにだけ効く。
- **遅延データの散らばり**: 遅れて届くデータが古いテーブル partition に散らばると、読むテーブル partition が増える。最悪でも全体照合と同じ費用で、それ以上にはならない。4 章と 5 章のテーブル partition 限定の金額は、1 日の書き込みがほぼ 1 日分のテーブル partition に入るという仮定。
- **効果が出る条件**: 絞り込みの効果は、書き込みのないテーブル partition を読まずに済むことから生まれる。モデルや地域のような属性だけで partition を切ると、毎回すべての partition に書き込みがあるので絞れない。partition 列に時間の要素（計測時刻の日や時間）を含める。
- **partition 列の一部だけ一致が保証される場合**: 一致が保証される列だけを照合の条件に使えば、partition 列の一部でも絞り込める（例: partition が「計測日、モデル、取り込み日」なら、計測日とモデルで照合する）。効果が出るのは、一致が保証される列に時間の要素が含まれる場合だけ。Firehose の upsert のように削除が partition の中でしか効かない仕組みでは、全 partition 列の一致が必要。
- **粒度**: テーブル partition を細かくすると 1 回に読む量は減るが、テーブル partition の数と小さいファイルが増える。
- **クエリの書き方**: 対象のテーブル partition を、クエリの条件に値で直接書く（例: `day(measured_at)` でテーブルの partition を切るなら、`measured_at` の範囲を書く）。結合条件から自動で絞り込まれるかはエンジンによって違う。
- **効かないこと**:
  - 同じメッセージのコピーが別々の Kafka の partition に入り、別々の Lambda が同時に処理する問題（PyIceberg の `upsert()`、Lambda から Athena の MERGE INTO）は残る。
  - 状態ストアや state で判定する案（DynamoDB、Valkey、直近 K 件リング、Kafka 内での重複排除など）は、テーブルを照合しないので効果がない。窓（TTL や K）の制約はそのまま残る。

## 3. 重複の発生源

| 種別 | 内容 | 防げる方式 |
|---|---|---|
| 1. 消費側の再配信 | ESM の再試行、リバランス、Lambda が commit した後に失敗した場合の再実行 | offset 冪等、キーによる重複判定 |
| 2. producer の再送 | ブローカーの ack が失われたことによる再送 | producer の idempotence、キーによる重複判定 |
| 3. デバイス側の再送 | 同じ `DeviceId + MessageID` が別のレコードとして再送される | キーによる重複判定のみ |

- キーによる重複判定は 3 種類すべてを防げる。この文書の案は主にこれを扱う。
- offset 冪等は種別 1 だけを防ぐ補助の方式である。

## 4. 案の比較（概要）

| 案 | 分類 | 落とせる重複の範囲 | 本テーブルへの重複の出方 | 現時点の評価 |
|---|---|---|---|---|
| 追記 + 定期重複排除ジョブ | 書き込み後 | 全期間 | ジョブ実行までは見える | 候補（流量が少なく、Lambda の commit が成り立つ場合） |
| staging + 定期 MERGE | 書き込み時 | 全期間 | 入らない。代わりにデータの反映が MERGE 間隔だけ遅れる | 候補（流量が少なく、Lambda の commit が成り立つ場合） |
| Parquet 出力 + 定期 MERGE | 書き込み時 | 全期間 | 入らない。代わりにデータの反映が MERGE 間隔だけ遅れる | **推奨** |
| Iceberg の branch を staging にする（WAP） | 書き込み時 | 全期間 | main には入らない。反映はジョブ間隔で遅れる | 非推奨（S3 Tables では branch があると snapshot の管理が止まる） |
| 直近 K 件リング | 書き込み前 | 同じデバイスの直近 K 件以内 | 窓外の重複は残る | 候補 |
| Valkey の時間窓 | 書き込み前 | TTL 内 | 窓外の重複は残る | 候補 |
| 共有 Bloom filter による振り分け | 書き込み前 | Bloom filter の保持期間内 | 窓外の重複は残る。窓内でも、2 つの経路の順序次第でまれに入る | 候補 |
| DynamoDB 条件付き Put | 書き込み前 | TTL 内 | 窓外の重複は残る | 候補（費用が課題） |
| Firehose への upsert 書き込み | 書き込み時 | 全期間（同一テーブル partition 条件が前提） | 入らない（delete file で読み取り時に除外） | 条件付き（流量が上限内の場合のみ） |
| PyIceberg の `upsert()` | 書き込み時 | 全期間（ただし自動再試行のある版では、同時実行時に漏れる） | 自動再試行のある版では、同時実行時に入る | 非推奨 |
| Lambda から Athena の MERGE INTO | 書き込み時 | 全期間 | 入らない見込み（commit 時の競合検証による） | 非推奨（MERGE どうしの衝突で処理が追いつかない、費用） |
| 読み取り時の重複排除 | 読み取り時 | 全期間（VIEW 経由のみ） | 残る | 非推奨 |
| バッチ内重複排除 | 書き込み前 | 同一バッチ内 | バッチをまたぐ重複は残る | 補助（必須） |
| offset 冪等 | 書き込み前 | 種別 1 のみ | 種別 2・3 は残る | 補助 |
| Kafka 内での重複排除（Lambda の前） | 基盤の追加 | TTL 内 | 窓外の重複は残る | 保留 |
| 正規化 topic 経由の重複排除（Lambda の後） | 基盤の追加 | TTL 内、または全期間（upsert の場合） | 方式次第 | 保留 |
| Flink で加工ごと処理 | 基盤の変更 | 方式次第 | 方式次第 | 保留（処理能力が未検証） |
| Kafka Connect Iceberg sink | 基盤の変更 | 未確定 | 未確定 | 保留 |
| Spark Structured Streaming | 基盤の変更 | 窓内、または全期間（MERGE の場合） | 方式次第 | 保留 |
| 圧縮バイトの着地 + バッチ ETL | 基盤の変更 | 全期間 | 入らない。反映はバッチ間隔で遅れる | 非推奨（再処理要件がない） |

Lambda が呼び出しごとに Iceberg へ commit する案（4.2 節で commit の共通費用が「かかる」案）は、基準ケースの流量では commit 頻度の問題（4.1 節）がある。表の評価は、この問題を解決できる場合（流量が少ない、commit をまとめられる）の評価である。

不採用・統合した案は 6 章に理由を書く。

### 4.1 費用試算の前提と単価

各案の「費用」は、次の基準ケースで試算している。流量、行サイズ、圧縮率、処理時間は仮定なので、実際の値が分かったら再計算する。

**金額の表記**

- 金額はすべて米ドル（USD）、税抜。円には換算していない。
- 費用はすべて月額で示す。1 か月は 30 日（720 時間、259.2 万秒）で計算する。
- 1 回ごとに課金される処理（MERGE、クエリなど）は、実行頻度を明記して月額に換算する。

**基準ケース**

- **リージョン**: 東京（ap-northeast-1）。
- **流量**: 機器 300 万台が 1 台 1 分に 1 メッセージを送る → 毎秒 5 万件、月 約 1,296 億件。
- **Kafka 上のメッセージ**: zlib 圧縮後 1 件 200 バイト → 月 約 25.9TB が Kafka を流れる。
- **行**: 1 メッセージ = 1 行（N=1）、加工後 200 バイト → 論理サイズで月 約 25.9TB。
- **圧縮**: Parquet で論理サイズの 1/3 → 月 約 8.6TB。キー 3 列（`DeviceId`、`MessageID`、書き込み ID）は圧縮後 1 行 約 30 バイト → 月 約 3.9TB。
- **Lambda**: ESM の batch size と batching window で 1 呼び出し 10,000 件にまとめる → 毎秒 5 回、月 約 1,296 万回。メモリ 2GB、加工は 1 件 0.5ms、Iceberg への commit は 1 回 2 秒。payload の上限は 6MB なので、圧縮後 1 メッセージ 600 バイト以下が条件。
- **commit**: 1 回の commit で 4 オブジェクト（データファイル 1、metadata 3）を書く。commit 回数は呼び出し回数と同じ。
- **保持**: 本テーブルは 1 か月（12 か月も併記）。Kafka の topic は 7 日、レプリカ 3。
- **テーブル partition**: 計測日などの日単位。テーブル partition 限定の金額は、1 日の書き込みがほぼ 1 日分のテーブル partition に入る（キー列で 1 日 約 0.13TB）と仮定する。遅れて届くデータが古いテーブル partition に散らばると、その分増える。
- **定期処理の頻度**: MERGE と重複排除ジョブは 1 日 1 回。
- **通信**: Lambda は Kafka に接続するため VPC 内で動く。S3 には Gateway Endpoint、S3 Tables の API にはインターフェース型 VPC エンドポイント（3 AZ）を使う。
- **S3 Tables のメンテナンス**: 既定の設定。snapshot は最大 120 時間保持され、参照されなくなったファイルは 3 日後に noncurrent、さらに 10 日後に削除される。そのため、コンパクション前の小さいファイルは約 18 日残る。

**commit に関わる費用の補足**

- 小さいファイルが約 18 日残るのは、古い snapshot が参照する期間（最大 120 時間、約 5 日）、参照がなくなってから noncurrent になるまで（unreferencedDays、既定 3 日）、noncurrent から削除まで（nonCurrentDays、既定 10 日）の合計。noncurrent の間もストレージとオブジェクト監視が課金される前提（未確認）。
- これらを短くすると、オブジェクト監視の費用は比例して下がる（合計 2 日なら約 90 ドル/月）。設定できる最小値は未確認。短くすると、過去の時点に戻れる範囲も短くなる。
- コンパクションの処理量の部分（約 86 ドル）は、commit 回数ではなくデータ量に比例する。commit の共通費用が「かからない」案でも、MERGE などが書いたファイルが sort compaction の対象になれば、この部分はかかる。
- Lambda の commit 待ち（約 860 ドル/月）は、全案に共通の費用の Lambda に含めている。commit に関わる費用の合計は、実質 約 2,060 ドル/月。

**commit 頻度の上限**（費用より大きな制約）

- Iceberg は、保持している snapshot をすべて metadata（metadata.json）に記録し、commit のたびに書き直す。基準ケースの毎秒 5 commit で、snapshot を既定の最大 120 時間保持すると、snapshot は約 216 万個になる。1 snapshot を数百バイトとすると、metadata は 1 commit ごとに GB 単位になり、「commit 1 回 2 秒」の前提が成り立たない。保持を 1 時間にしても約 1.8 万個残る。
- PyIceberg は commit のとき、読み込んだ時点の snapshot がまだ最新かを検証する。複数の Lambda が同時に commit すると、後の commit は失敗して再試行になる。
- そのため、Lambda が呼び出しごとに commit する構成は、基準ケースの流量では成り立たない見込み。commit を Lambda の外に出す（Parquet 出力 + 定期 MERGE）か、流量が少なく commit の回数を抑えられる場合に限る。上限は実測が必要（11 章）。

**含めていない費用**: 既存の EKS 上の Kafka（ノード、EBS、レプリケーションの AZ 間転送）、KMS、CloudWatch Logs。新しい topic を追加する案は、追加する topic の分を各案の費用に含めている。

## 5. 各案の詳細

### 5.1 書き込み前に判定する案

#### バッチ内重複排除

- **仕組み**: Lambda が受け取った 1 バッチの中で、`message_key` が同じメッセージを 1 つにまとめてから書き込む。
- **落とせる範囲**: 同一バッチ内のみ。
- **メリット**: 追加の部品が不要で、費用はほぼゼロ。他のどの案とも併用できる。
- **デメリット**: バッチをまたぐ重複は防げない。
- **費用**: 追加の課金はほぼない（ほぼ 0 ドル/月）。Lambda の実行時間がわずかに増えるだけで、全案に共通の Lambda の費用に含まれる。

#### DynamoDB 条件付き Put

- **仕組み**: メッセージごとに `message_key` を条件付き Put（`attribute_not_exists`）で登録し、登録できたメッセージだけを書き込む。TTL で古いキーを消す。
- **落とせる範囲**: TTL 内。
- **前提・制約**:
  - 判定はメッセージ単位で、1:N でも N 倍にはならない。
  - commit 前に登録するため、commit 前に Lambda が落ちると、再配信されたメッセージが重複と誤判定されて欠落する。直近 K 件リングと同じ予約方式（pending、座標、リース期限）で回避する必要がある。
- **メリット**: 判定が厳密。マネージドで運用が軽い。状態が失われない。
- **デメリット**:
  - 書き込み費用が流量に比例する（基準ケースでオンデマンド 約 185,000 ドル/月。下の「費用」を参照）。
  - TTL を超えて遅れた重複は漏れる。TTL を付けなければ全期間になるが、保存量が増え続ける（基準ケースで 1 日 約 432GB）。
- **費用**:
  - 共通費用: 全案に共通の費用に加えて、commit の共通費用（約 1,200 ドル/月）がかかる。
  - 書き込みの回数: 予約方式では、1 メッセージにつき予約と完了の印付けの 2 回書き込むので、月 約 2,592 億 WRU。条件で失敗した書き込みも WRU を消費する。
  - 書き込み（オンデマンド）: 2,592 億 WRU × 0.715 ドル/百万で **約 185,000 ドル/月**。
  - 書き込み（プロビジョンド）: 平均 10 万 WCU × 0.000742 ドル/時 × 720 時間で **約 53,000 ドル/月**。ピークに備えた余裕の分は上乗せになる。リザーブドキャパシティで下げられる（割引率は未確認）。
  - ストレージ（TTL 24 時間、1 件 約 100 バイト）: 約 432GB で約 120 ドル/月。TTL を延ばしても増えるのはストレージだけで、7 日で約 860 ドル/月、30 日で約 3,700 ドル/月。費用は TTL より流量で決まる。
  - TTL を付けず全期間にすると、保存量が 1 日 約 432GB ずつ増える。1 年後には約 158TB で、ストレージだけで約 45,000 ドル/月になる。
  - Lambda の実行時間: 条件付きの書き込みは `BatchWriteItem` ではできず（トランザクションにすると WRU が 2 倍）、1 件ずつ `PutItem` を呼ぶ。並列に呼んでも 1 呼び出しあたり 1〜2 秒延びるとして、約 430〜860 ドル/月（推定）。
  - 合計（commit の共通費用を除く）: **オンデマンド 約 186,000 ドル/月**、**プロビジョンド 約 54,000 ドル/月**。

#### Valkey の時間窓（`SET NX EX`）

- **仕組み**: `message_key` を `SET NX EX`（キーがなければ TTL 付きで登録）で登録し、登録できたメッセージだけを書き込む。
- **落とせる範囲**: TTL 内。
- **前提・制約**:
  - 保存するキー数は `流量 × TTL`。
  - 欠落を避ける予約方式は DynamoDB と同じ考慮が必要。
  - Lambda から ElastiCache などに接続できるネットワーク経路が必要。
- **メリット**: 低遅延で高スループット。TTL をメモリ量（費用）に合わせて調整できる。
- **デメリット**:
  - メモリ量が流量と TTL に比例する（基準ケースの TTL 24 時間で約 216〜432GB）。
  - TTL を超えて遅れた重複は漏れる。
  - ノード障害で状態を失うと、その間の重複が漏れる。
- **費用**:
  - 共通費用: 全案に共通の費用に加えて、commit の共通費用（約 1,200 ドル/月）がかかる。
  - 保存するキーは 1 日分の約 43.2 億キー。1 キー 50〜100 バイトとして約 216〜432GB。
  - 操作の回数: 予約方式では、1 メッセージにつき予約と完了の印付けの 2 回操作する。
  - AZ 間転送: Lambda と Valkey が別の AZ にあると、往復の通信に課金される。1 メッセージあたり往復 約 200 バイト、3 分の 2 が AZ をまたぐとして、約 350 ドル/月。
  - サーバーレス: ストレージ（216〜432GB × 0.101 ドル/時 × 720 時間）が約 15,700〜31,400 ドル/月、ECPU（1 操作 1 ECPU × 2 回）が約 700 ドル/月。AZ 間転送と合わせて **約 17,000〜32,000 ドル/月**。
  - ノード型: cache.r7g.4xlarge（105.81GiB、予約メモリ 25% を除くと約 79GiB、1.6744 ドル/時）をプライマリ 3〜6 台、それぞれにレプリカ 1 台で約 7,200〜14,500 ドル/月。AZ 間転送と合わせて **約 7,600〜15,000 ドル/月**。レプリカなしなら半額近くになるが、ノード障害で状態を失う。SSD を併用するデータ階層化のノードで下げられる可能性がある（単価は未取得）。
  - TTL を 1 時間にすると、保存量は約 9〜18GB。サーバーレスで約 1,700〜2,400 ドル/月、ノード型（cache.r7g.xlarge 2 台）で約 950 ドル/月（どちらも AZ 間転送を含む）。費用は流量 × TTL で決まるので、TTL を短くするのが最も効く。

#### 直近 K 件リング

- **仕組み**: デバイスごとに、直近 K 件の `MessageID`（固定長のハッシュ）を Valkey に保持する。新しい `MessageID` がリングにあれば重複、なければリングに追加して最も古いものを押し出す。判定と追加は Lua スクリプトで原子的に行う。
- **落とせる範囲**: 同じデバイスの直近 K 件以内。
- **前提・制約**:
  - 同じデバイスのメッセージが別々の Lambda で同時に処理され得るため、判定と追加は原子的でなければならない。
  - commit 前に Lambda が落ちても欠落しないよう、予約に状態（pending / done）、座標、リース期限を持たせる。
    - 同じ座標で再配信されたら、自分自身の再試行とみなして書き込みを許可する。
    - 別の座標で来て、既存が pending かつリース期限内なら、重複として捨てる。
    - 別の座標で来て、既存が pending かつリース期限切れなら、元の処理が失敗したとみなし、新規として扱う。
    - commit が成功したら done にする。
  - K は、デバイスの送信頻度と再送の遅れから決める（現時点では不明）。
- **メリット**:
  - 状態の大きさが流量に依存しない（デバイス数 × K × ハッシュ長）。試算例: 300 万台 × K=64 × 8 バイトで約 1.5GB（固定長で詰めた場合）。
  - 窓が件数で決まるので、まれにしか送らないデバイスほど実時間の窓が長くなる。
- **デメリット**:
  - K 件より古い再送は漏れる。
  - 状態を失うと、その間の重複が漏れる。
  - 予約処理の設計が複雑。
  - Valkey への操作回数は流量に比例する（Lua を含む負荷は未計測）。
- **費用**:
  - 共通費用: 全案に共通の費用に加えて、commit の共通費用（約 1,200 ドル/月）がかかる。
  - 保存量は約 2GB（K=64 のリング 約 1.5GB と、キーごとのオーバーヘッド）。サーバーレスのストレージは約 150 ドル/月。
  - ECPU: Lua で 512 バイトのリングを読み書きするので、1 操作 1〜5 ECPU と仮定する。予約と完了の印付けで 1 メッセージ 2 回操作するので、約 700〜3,500 ドル/月。
  - AZ 間転送: Valkey の時間窓と同じく約 350 ドル/月。
  - 合計: サーバーレスで **約 1,200〜4,000 ドル/月**。ノード型なら cache.r7g.xlarge 2 台と AZ 間転送で **約 950 ドル/月** だが、毎秒 10 万回の Lua を 1 ノードでさばけるかは要検証（足りなければシャードを増やす）。

#### 共有 Bloom filter による振り分け

- **仕組み**: ElastiCache（Valkey 8.1 以降）の Bloom filter に `message_key` を `BF.ADD` する。`BF.ADD` は「新しく追加した」か「既にあったかもしれない」かを原子的に返すので、その結果で書き込み先を振り分ける。
  - **新しく追加した**: 確実に初出なので、本テーブルへそのまま書く。
  - **既にあったかもしれない**: 重複か偽陽性のどちらか。捨てずに「疑わしい行」として staging（または Parquet）に書き、定期 MERGE で本テーブルにない行だけを入れる。
- **落とせる範囲**: Bloom filter を保持している期間内。日ごとに filter を作り、直近 D 日分で判定する、などで期間を決める。
- **前提・制約**:
  - 偽陽性で初出のメッセージを捨てないよう、疑わしい行は必ず確認の経路に回す。
  - 1 つの Bloom filter は 128MB までなので、キーのハッシュで多数の filter に分ける。複数の filter をまとめて判定する場合は、Lua で原子的に行う。
  - 直接書く経路の commit より先に MERGE が走ると、同じメッセージが両方の経路から入り得る。疑わしい行は一定時間置いてから MERGE する。ただし保証ではないので、定期重複排除ジョブと併用する。
- **メリット**:
  - 正確なキーを保存するより、メモリが大幅に少ない。基準ケースの 24 時間分で約 10GB と、Valkey の時間窓（約 216〜432GB）の 1/20 以下になる。
  - 疑わしい行も捨てないので、データの欠落が起きない。commit 前に Lambda が落ちても、再配信は確認の経路に回るだけなので、予約方式が要らない。
  - 大半のメッセージ（初出）は、即時に本テーブルへ入る。
- **デメリット**:
  - 経路が 2 つ（直接の経路と確認の経路）になり、構成が複雑。
  - 疑わしい行は反映が遅れる。偽陽性率に応じて、確認の経路の量が増える。
  - 保持期間を超えて遅れた重複は、「新しく追加した」と判定されて本テーブルに入る。
- **費用**:
  - 共通費用: 直接書く経路が Iceberg に commit するので、commit の共通費用（約 1,200 ドル/月）がかかる。
  - Bloom filter: 偽陽性率 1% で 1 キー 約 1.2 バイト。24 時間分は約 5.2GB で、日ごとの filter を 2 つ持つと約 10GB。サーバーレスのストレージ 約 730 ドル/月、ECPU 約 350 ドル/月（予約方式が要らないので 1 メッセージ 1 回）、AZ 間転送 約 350 ドル/月で、**約 1,400 ドル/月**（ノード型なら cache.r7g.xlarge 2 台と AZ 間転送で約 950 ドル/月）。
  - 確認経路: 偽陽性と真の重複（全体の 1% 強）を Parquet に書き（PUT 約 60 ドル/月）、毎日の MERGE で本テーブルと照合する。全体照合では、確認する件数が少なくても本テーブル側のキー列の読み取りは減らないので、MERGE は 1 か月保持で約 590 ドル/月、12 か月保持で約 7,000 ドル/月。テーブル partition 限定なら、疑わしい行が入るテーブル partition（ほぼ 1 日分）だけを読むので約 20 ドル/月。
  - 合計（commit の共通費用を除く）: **約 1,500 ドル/月**（テーブル partition 限定）、**約 2,100 ドル/月**（全体照合、1 か月保持）、**約 8,500 ドル/月**（全体照合、12 か月保持）。

### 5.2 書き込み時にテーブル側で防ぐ案

#### staging + 定期 MERGE

- **仕組み**: Lambda は書き込み ID を付けて staging テーブルに追記するだけにする。定期ジョブは、staging 内でメッセージごとに 1 つの書き込み ID の行だけを残し、本テーブルへ `MERGE INTO`（`DeviceId, MessageID` が本テーブルにない行だけ `INSERT`）してから、処理済みの staging を消す。
- **落とせる範囲**: 全期間。
- **本テーブルへの出方**: 本テーブルには重複が入らない。代わりに、データの反映が MERGE の間隔だけ遅れる。
- **前提・制約**:
  - 同一テーブル partition 条件が成り立てば、テーブルの partition 列も照合条件に入れ、staging に含まれるテーブル partition だけと照合できる（2.6 節）。成り立たなければ本テーブル全体と照合し、sort order による絞り込みに頼る。
  - MERGE は 1 本に直列化する（同時に走らせない）。
  - Lambda は staging に呼び出しごとに commit するので、commit 頻度の問題（4.1 節）は staging のテーブルで起きる。
  - Athena の `MERGE INTO` は merge-on-read（positional delete）で動作する。
- **メリット**: 本テーブルが常に重複なしになる。Lambda は追記だけで軽い。MERGE が直列なので、同時実行の問題が出ない。
- **デメリット**: データの反映が遅れる。テーブルが 2 つになる。全体照合では、保持期間に比例して MERGE の費用が増える。
- **費用**:
  - 共通費用: Lambda が staging に commit するので、commit の共通費用（約 1,200 ドル/月）がかかる。staging はすぐ消すデータなので、staging のコンパクションは止めてもよい。
  - MERGE の読み取り（Athena、1 日 1 回）: staging は 1 日分（圧縮後 約 0.29TB）で約 43 ドル/月。本テーブルはキー列だけを読む。
    - テーブル partition 限定: staging に含まれるテーブル partition（ほぼ 1 日分、約 0.13TB）だけを読むので、保持期間に関係なく約 20 ドル/月。合計 **約 60 ドル/月**。
    - 全体照合: 1 か月保持（約 3.9TB）で約 590 ドル/月、12 か月保持（約 46.7TB）で約 7,000 ドル/月。合計 **約 600 ドル/月**（1 か月保持）、**約 7,000 ドル/月**（12 か月保持）。
  - MERGE を 1 時間ごとに実行すると、全体照合では本テーブルの読み取りが 24 倍になり、1 か月保持でも約 14,000 ドル/月になる。テーブル partition 限定なら、毎回当日のテーブル partition（平均 約 65GB）を読むので約 280 ドル/月。

#### Parquet 出力 + 定期 MERGE

- **仕組み**: Lambda は加工した行を、Iceberg ではなく通常の S3 バケットに Parquet ファイルとして書く（1 バッチ 1 ファイル）。定期ジョブが Parquet を読み、メッセージごとに 1 つのファイルの行だけを残してから、本テーブルへ `MERGE INTO`（`DeviceId, MessageID` が本テーブルにない行だけ `INSERT`）する。
- **落とせる範囲**: 全期間。
- **本テーブルへの出方**: 本テーブルには重複が入らない。代わりに、データの反映が MERGE の間隔だけ遅れる。
- **staging + 定期 MERGE との違い**: staging が Iceberg テーブルではなく Parquet ファイルになり、Lambda は Iceberg に commit しない。
- **前提・制約**:
  - Athena から読む場合は、Parquet の置き場を Glue Data Catalog の外部テーブルとして登録する。Spark などで読んでもよい。
  - 書き込み ID は、Parquet ファイルのオブジェクトキーで代用できる（Athena の `"$path"` 疑似列）。
  - ファイル名は UUID にするか、Kafka の座標から決める。座標から決めると、同じ範囲の再試行は同じファイルの上書きになる。
  - どのファイルを処理済みにしたかを管理する。例: 書き込み時刻で prefix を分け、書き込みが終わった prefix だけを処理する。同じファイルを 2 回処理しても、MERGE は本テーブルにないキーしか入れないので、重複は入らない。
  - MERGE は 1 本に直列化する。Lambda ごとに MERGE すると、MERGE どうしが衝突して処理が追いつかない（Lambda から Athena の MERGE INTO を参照）。
  - 照合範囲は staging + 定期 MERGE と同じ。同一テーブル partition 条件が成り立てば、Parquet に含まれるテーブル partition だけと照合できる。
  - **MERGE の間隔**: 間隔を短くするほど反映は速くなるが、MERGE のたびに当日（または当該時間）のテーブル partition を読む。間隔を短くするなら、テーブル partition を時間単位にする。1 回の MERGE が間隔内に終わる必要がある（費用は下の表）。
  - **遅延データが多い場合**: 遅れて届くデータが多くの時間帯に散らばると、1 回の MERGE で読むテーブル partition が増える。その場合は経路を 2 つに分ける。直近のテーブル partition の行は短い間隔の MERGE で、古いテーブル partition の行は別の prefix に回して 1 日 1 回の MERGE で入れる。2 つの MERGE が触るテーブル partition は重ならないので衝突しない。古い時刻のデータは反映が遅れる。
  - **ジョブの中身**: どのエンジンで実装しても、ジョブがすることは 2 つ。(1) 照合: 新しい行のキーを、新しい行どうしと、本テーブルの該当するテーブル partition と照合する。(2) 反映: 重複でない行を本テーブルに入れる。エンジン（Athena、EMR）と反映の方法（MERGE の `INSERT`、`add_files`）は実装の選択で、重複の落とし方は変わらない。
  - **MERGE を実行するエンジン**: Athena と EMR（Spark）のどちらでもよい。
    - Athena: クラスタが要らず、SQL 1 文で書ける。課金はスキャン量に比例する。commit 時に競合を検証する（Trino の実装）。Iceberg は 1.4.2 で、v2 のテーブルだけを扱う。
    - EMR（Spark）: 課金は実行時間に比例し、読む量が増えたときの伸びが緩やか。ファイルの大きさや並びを制御できる。Structured Streaming のファイル入力を使えば、処理済みファイルを checkpoint が管理し、スケジューラも要らない。EMR on EKS なら既存の EKS で動かせる。v3 も使えるが、v3 にすると Athena がテーブルを読めなくなる。
    - まず Athena で実行時間と読み取り量を測る。MERGE の SQL は Spark SQL でもほぼそのまま動くので、後から移す手間は小さい。
  - **トリガーと 1 本ずつの制御**: EventBridge Scheduler も Step Functions も、前回の実行が終わったかを見ずに次を起動する。1 本ずつにする仕組みを別に入れる。
    - EMR: Scheduler から `StartJobRun` を直接呼び、EMR 側の同時実行数を 1 にする（EMR Serverless の `maxConcurrentRuns`、EMR on EKS の `maxConcurrentJobRuns`、EMR on EC2 のステップの同時実行数）。重なった起動は待ち行列に入る。処理の中身（対象の partition の算出、処理済みファイルの管理）は Spark のジョブに書けるので、トリガーは起動するだけでよい。
    - Athena: Scheduler から `StartQueryExecution` を直接呼べるが、完了を待てず、同時実行も制御できず、SQL も毎回同じになる。Step Functions（ロックか、1 つの実行の中での繰り返しで 1 本ずつにする）、Lambda、EKS の CronJob（`concurrencyPolicy: Forbid`）のどれかから実行する。
    - Scheduler は同じ起動を 2 回届けることがある（at-least-once）。冪等性のトークン（EMR Serverless の `clientToken`、Athena の `ClientRequestToken`）に Scheduler の実行 ID を渡す。
  - **読む側の差分抽出**: 行に MERGE の実行 ID を付けると、読む側はそれで差分を抽出できる（8 章）。
  - 処理済みの Parquet は、S3 のライフサイクルで消す。
  - 反映を MERGE ではなく `add_files` にする方法もある（下記）。
- **メリット**:
  - Lambda は S3 にオブジェクトを書くだけになり、commit の競合と commit 頻度の問題（4.1 節）がなくなる。PyIceberg の commit 再試行も不要になる。
  - S3 のオブジェクト書き込みはアトミックなので、途中までのファイルは見えない。
  - 本テーブルへの commit が MERGE の実行ごとに 1 回にまとまり、小さいファイルと snapshot の数が減る。
  - 加工は Lambda に残せる。
  - 本テーブルが常に重複なしになる。
- **デメリット**:
  - データの反映が遅れる。
  - Parquet の置き場、Glue の外部テーブル、MERGE ジョブ、処理済みの管理が増える。
  - 全体照合では、保持期間に比例して MERGE の費用が増える（staging + 定期 MERGE と同じ）。
- **費用**:
  - 共通費用: Lambda は Iceberg に commit しないので、commit の共通費用はかからない。commit 待ちもなくなるので、全案に共通の Lambda の費用が約 800 ドル/月下がる。
  - S3 PUT: 1 呼び出しで 1 ファイルなので、月 約 1,296 万 PUT × 0.0047 ドル/1,000 件で **約 60 ドル/月**。1 呼び出し 100 件のまま（毎秒 500 回）だと約 6,100 ドル/月。
  - staging の保存: 1 日分（圧縮後 約 0.29TB）を S3 標準で保持して約 7 ドル/月。
  - MERGE の読み取り: staging + 定期 MERGE と同じ（テーブル partition 限定で約 60 ドル/月、全体照合で 1 か月保持なら約 600 ドル/月、12 か月保持なら約 7,000 ドル/月）。
  - 合計: **約 130 ドル/月**（テーブル partition 限定）、**約 700 ドル/月**（全体照合、1 か月保持）、**約 7,100 ドル/月**（全体照合、12 か月保持）。
  - MERGE の間隔を短くした場合は、下の表のとおり。

MERGE の間隔と Athena の読み取りの月額（テーブル partition 限定。PUT と staging の保存 約 70 ドル/月は別）:

| MERGE の間隔 | 日単位のテーブル partition | 時間単位のテーブル partition |
|---|---|---|
| 1 日 1 回 | 約 60 ドル | 約 60 ドル |
| 1 時間 | 約 280 ドル | 約 60 ドル |
| 5 分 | 約 2,900 ドル | 約 160 ドル |
| 1 分 | 約 14,000 ドル | 約 630 ドル |

毎回、当日（時間単位なら当該時間）のテーブル partition の途中までを読む（平均で日単位 約 65GB、時間単位 約 2.7GB）として計算した。遅延データが散らばると増える。

**反映の方法を `add_files` にする場合**

照合は上と同じで、照合の結果を本テーブルに反映する方法だけが違う。MERGE は重複でない行を本テーブルに書き直すが、`add_files` は Lambda が書いたファイルをそのまま本テーブルのデータファイルとして登録する。

- **反映の流れ**:
  1. Lambda は Parquet を本テーブルの場所に書く（commit はしない）。照合用に、テーブル partition 列、`DeviceId`、`MessageID` とファイルのパスだけの小さなファイルを、通常の S3 バケットに書く。
  2. ジョブは照合で、重複を含むファイルを特定する。
  3. 重複のないファイルは、そのまま PyIceberg の `add_files` で登録する（大半のファイル）。
  4. 重複を含むファイルは、重複行を除いて書き直してから登録する。元のファイルは未登録のまま残し、未参照ファイルの削除に任せる。
  5. 1 回の実行で 1 回だけ commit する。
- **前提・制約**:
  - `add_files` は行の中身を見ない（ファイルのフッタだけを読む）。`check_duplicate_files` が調べるのは、同じパスのファイルが登録済みかどうかだけ。重複の判定は照合で行う。
  - `add_files` は append として commit する。各 Lambda が照合してから `add_files` する形は、呼び出しごとに本テーブルを読むうえ、PyIceberg の自動再試行が append を検証せずに載せ替えるので、同時実行時に重複が入る。照合と登録は 1 本のジョブで行う。
  - S3 Tables のテーブルの場所で使える API は PutObject、GetObject、HeadObject と multipart の操作だけで、ListObjects がない。ジョブは、Lambda が別の場所に記録したパス（照合用の小さなファイルなど）からファイルを知る必要がある。
  - 未登録のファイルは未参照のファイルとして扱われ、既定では 3 日後に noncurrent、その 10 日後に削除される。ジョブが長く止まると、未登録のファイルを失うおそれがある（作成日から数えるかは未確認）。
  - 1 ファイルには 1 つのテーブル partition の行だけを入れる（`add_files` は partition の値をフッタの統計から推定する）。スキーマはテーブルと一致させ、field ID がなければ name mapping で対応付ける。
- **MERGE と比べたメリット**: データを書き直さないので、ジョブが速く、間隔を短くしやすい。
- **MERGE と比べたデメリット**:
  - 振り分け、書き直し、登録を自前で実装する。MERGE なら SQL 1 文で済む。
  - Lambda が書いた小さいファイルがそのまま本テーブルに入るので、小さいファイルが多い（MERGE は 1 回分をまとめて書く）。
  - ジョブの停止が長引くと、未登録のファイルが消えるおそれがある。
- **費用**（5 分ごと、時間単位のテーブル partition 限定）: S3 PUT（データの Parquet と照合用のファイル）約 120 ドル/月、照合の読み取り（Athena）約 140 ドル/月、小さいファイルのオブジェクト監視 約 190 ドル/月とコンパクションのオブジェクト課金 約 24 ドル/月で、**約 480 ドル/月**。MERGE で反映する場合（約 230 ドル/月）より高い。利点は費用ではなく、ジョブの速さにある。

#### Iceberg の branch を staging にする（WAP）

- **仕組み**: Lambda は本テーブルの別の branch（例: audit）に追記する。定期ジョブが branch 上で重複を除き、main branch に反映する（Write-Audit-Publish）。
- **落とせる範囲**: 全期間。
- **本テーブルへの出方**: main には重複が入らない。反映はジョブ間隔で遅れる。
- **前提・制約**:
  - S3 Tables では、利用者が作った branch やタグが 1 つでもあると、テーブル全体の snapshot の管理（古い snapshot の削除）が失敗する。この案は branch を使うので、snapshot の管理を自前で行う必要がある。
  - PyIceberg と Athena が branch への書き込みと読み取りに対応しているかは要確認。
  - Lambda の追記と重複除去が同じ branch に入るので、どの snapshot までを main に反映するかの管理が必要。
- **メリット**: staging のテーブルが要らず、テーブルが 1 つで済む。main は常に重複なしになる。
- **デメリット**:
  - Lambda は引き続き Iceberg に commit するので、commit 競合は残る。
  - branch の操作に対応したエンジン（Spark など）が必要になる可能性が高い。
  - 設計と運用が複雑。
- **費用**:
  - 共通費用: Lambda の commit は残るので、commit の共通費用（約 1,200 ドル/月）がかかる。
  - 定期ジョブの読み取り: 追記 + 定期重複排除ジョブと同程度（テーブル partition 限定で約 40 ドル/月、全体照合で 1 か月保持なら約 1,200 ドル/月、12 か月保持なら約 14,000 ドル/月）。
  - audit branch の保存: branch の snapshot を 1 日で消すと、増える保存量は 1 日分（約 0.29TB）で約 8 ドル/月。
  - 合計（commit の共通費用を除く）: **約 50 ドル/月**（テーブル partition 限定）、**約 1,200〜14,000 ドル/月**（全体照合）。

#### Firehose への upsert 書き込み

- **仕組み**: Lambda は加工した行を Firehose（Direct PUT）に送り、Firehose が unique keys（`DeviceId`、`MessageID`、行識別子）で upsert する。Firehose は delete file を書いてから insert する（equality delete）。
- **落とせる範囲**: 全期間（同一テーブル partition 条件が前提）。
- **本テーブルへの出方**: 古いコピーは delete file によって読み取り時に除外され、S3 Tables の compaction で物理的に消える。
- **前提・制約**:
  - Firehose の delete file は、レコード自身のテーブル partition にだけ書かれる（テーブル partition をまたぐ削除は非対応）。同一テーブル partition 条件が成り立たないと、別のテーブル partition にある古いコピーは消えない。
  - upsert を使う stream の最大スループットは、バージニア北部・オレゴン・アイルランドで 5 MiB/秒、その他のリージョン（東京を含む）で 1 MiB/秒。上限の緩和は追記専用の場合に限られる。
  - 同じテーブルへ複数の stream で書くことは非推奨（楽観的同時実行制御で commit が競合する）。そのため実質的に、1 テーブルあたり上記の上限になる。
  - 1 レコードに 1 JSON オブジェクトしか入れられず、列名と型がテーブルと完全に一致する必要がある。
  - Firehose が使う Iceberg ライブラリは 1.5.2。
  - 上の上限は Direct PUT の場合。Lambda → Kinesis Data Streams → Firehose にすると Direct PUT の上限は当てはまらないが、Iceberg の update / delete を使う場合の上限は要確認。
- **メリット**: 状態ストアが不要。窓の制約がない。commit を Firehose がまとめる。
- **デメリット**:
  - 上限が規模に合わない可能性が高い。試算例: 1 行 200 バイトなら、1 MiB/秒で約 5,000 行/秒。
  - delete file の分だけ、S3 の PUT 費用と読み取りコストが増える。
  - PyIceberg は equality delete を含むテーブルを読めないとされており、このテーブルを PyIceberg で読む処理（重複排除ジョブなど）を作れない（現行版の対応状況は要確認）。
  - 書き込み経路が PyIceberg から Firehose に変わる。
- **費用**:
  - 共通費用: commit は Firehose が行うので、commit の共通費用はかからない。
  - 取り込み: Firehose は JSON で受け取るので、1 行 200〜400 バイトとすると月 約 25.9〜51.8TB。Iceberg 宛て Direct PUT の 0.093 ドル/GB（月 256TB まで）で **約 2,400〜4,800 ドル/月**。
  - delete file の PUT は少なく、無視できる。ただし delete file の分だけ、コンパクションの処理量が増える。
  - 注意: 毎秒 5 万件 × 200〜400 バイト = 10〜20MB/秒で、東京の上限 1 MiB/秒の約 10〜20 倍。同じテーブルへの複数 stream は非推奨なので、この上限を満たせない限り、上の金額は成立しない。

#### PyIceberg の `upsert()`

- **仕組み**: Lambda がバッチごとに PyIceberg（0.9.0 以降）の `upsert()` を呼ぶ。テーブルからキーが一致する行を読み、既存の行は上書きし、ない行は追加する。
- **落とせる範囲**: 全期間（ただし同時実行時は漏れる）。
- **前提・制約**:
  - join 列は行を一意に識別できる必要がある。`DeviceId, MessageID` だけでは N 行が同じキーになり、入力の重複としてエラーになる。行識別子を join 列に加える。
  - PyIceberg の削除は copy-on-write で、該当するファイルを書き直す。
  - PyIceberg は commit のとき、読み込んだ時点の snapshot がまだ最新かを検証し、違えば失敗する。PR #3320（2026-08-12 に main へマージ。どのリリースに入ったかは未確認）以降は、最新の snapshot に載せ替えて自動で再試行する（`commit.retry.num-retries`、既定 4 回）。載せ替えのとき、append（行の追加）は競合を検証しない。overwrite と delete は、分離レベルが serializable なら、追加されたファイルとの競合を検証する。
- **メリット**: 追加の部品が不要で、実装が短い。
- **デメリット**:
  - 同じキーを 2 つの Lambda が同時に upsert すると、どちらも「既存の行なし」と判断する。重複が起きる幅は、既存行を読んでから commit が終わるまでの時間で、数秒から数十秒ある（ミリ秒単位ではない）。時間は送信時刻ではなく処理時刻なので、Kafka の partition ごとの処理の遅れが違えば、離れて送られたコピーも同時に処理され得る。
    - 自動で再試行しない版: 後の commit が失敗する。アプリケーションが `upsert()` を呼び直せば読み直すので、重複は入らないが、commit の失敗が多発する。
    - 自動で再試行する版: 両方が「既存行なし」と判断した場合は追加（append）だけになり、検証されずに載せ替えられるので、両方の行が入って重複する。
    - 同時処理が起きるのは種別 3 だけ。種別 1・2 は同じ Kafka の partition に入り、ESM が順に処理する。同じメッセージのコピーは別々の Kafka の partition に入り得る（2.2 節）ので、種別 3 では起こり得る。テーブル partition で照合範囲を絞っても、この問題は残る。
  - キーがテーブルの partition ではないので、照合のための読み取り範囲が広い。テーブル partition で絞っても、呼び出しのたびに当日のテーブル partition を読む。
  - ファイルの書き直しと commit 競合が増え、規模的に厳しい。
- **費用**:
  - 共通費用: commit の共通費用（約 1,200 ドル/月）がかかり、copy-on-write でファイルを書き直す分の PUT とコンパクションが加わる。
  - 照合の読み取りが支配的になる。本テーブルのキー列は 1 日分でも約 130GB あり、照合範囲を当日のテーブル partition に絞っても、1 回の呼び出しでこれを読むことになる。Lambda の実行時間の上限（15 分）と S3 の GET の量で成立しないため、月額は出せない。下限は commit の共通費用の約 1,200 ドル/月。

#### Lambda から Athena の MERGE INTO

- **仕組み**: Lambda がバッチを staging（Iceberg テーブルか Parquet）に書いたあと、Athena の `MERGE INTO` を呼んで、本テーブルにない行だけを入れる。
- **落とせる範囲**: 全期間。
- **前提・制約**:
  - Athena の MERGE は入力元にテーブルが必要なので、バッチごとに staging への書き込みと MERGE の 2 段階になる。
  - ESM は Kafka の partition の数だけ Lambda を同時に起動するので、MERGE も同時に走る。Trino（Athena のエンジンの元）の MERGE は、commit のとき、読み込んだ snapshot 以降に同じテーブル partition へデータファイルが追加されていれば失敗する（分離レベルの既定が serializable）。失敗した MERGE をやり直せば読み直すので、同じキーが二重に入ることはない見込み。Athena で同じ動きかは未確認。
  - その代わり、どの Lambda のバッチにも当日のテーブル partition の行が含まれるので、同時に走る MERGE はほぼ必ず衝突し、実質 1 本ずつしか成功しない。処理能力は「バッチの件数 ÷ MERGE 1 回の時間」で、1 回 10 秒なら毎秒 1,000 件。基準ケースの毎秒 5 万件に届かず、ESM のバッチの上限（10,000 件、6MB）のためバッチを大きくして補うこともできない。
  - MERGE を 1 本に直列化し、複数のバッチをまとめて MERGE すれば衝突はなくなる。それが Parquet 出力 + 定期 MERGE（間隔を短くした場合）である。
- **メリット**: 本テーブルへの反映が速い（バッチごと）。
- **デメリット**:
  - MERGE のたびに本テーブルとキーを照合するので、バッチの頻度に比例して費用が増える。キーでテーブルの partition を切らないので、テーブル partition で絞っても、毎回当日のテーブル partition を読む。
  - Athena の同時実行クエリ数の上限（Service Quotas）に当たる。
  - クエリに数秒以上かかり、Lambda の処理時間が延びる。
  - MERGE どうしの衝突で処理が追いつかない（上記）。
- **費用**:
  - 共通費用: staging を Iceberg にする場合は、commit の共通費用（約 1,200 ドル/月）がかかる。
  - Athena: 呼び出しごとに MERGE を走らせると、月 約 1,296 万回になる。最小課金（10MB/クエリ、0.00005 ドル/回）だけでも約 650 ドル/月。
  - テーブル partition 限定でも、毎回当日のテーブル partition のキー列を読む。日単位のテーブル partition（平均 約 65GB）なら **約 420 万ドル/月**、時間単位（平均 約 2.7GB）でも **約 18 万ドル/月** で、成立しない。
  - 全体照合で本テーブルのキー列（1 か月保持で約 3.9TB）を毎回読むと、約 2.5 億ドル/月。

### 5.3 書き込み後・読み取り時に消す案

#### 追記 + 定期重複排除ジョブ

- **位置づけ**: 既存の処理（Lambda が PyIceberg で本テーブルに直接 append）をほぼそのまま残し、登録後に重複を消すジョブを後付けする案。
- **仕組み**:
  1. Lambda は重複を含めたまま、登録日時の列を付けて追記する（2.2 節）。
  2. 定期ジョブが、前回の実行以降に書き込みがあったテーブル partition を、snapshot の履歴から求める（下記）。
  3. その partition で、`DeviceId + MessageID` が同じで登録日時が異なる行を探し、最初に登録したコピーを残す。そのコピーの N 行はすべて残る。
  4. 残さないコピーの行を消す。

  Athena で書く場合の例（実装時に要検証）:

  ```sql
  MERGE INTO main t
  USING (
    SELECT DISTINCT dt, DeviceId, MessageID, registered_at
    FROM (
      SELECT dt, DeviceId, MessageID, registered_at,
             DENSE_RANK() OVER (PARTITION BY dt, DeviceId, MessageID ORDER BY registered_at) AS rk
      FROM main
      WHERE dt IN (...)          -- 前回以降に書き込みがあったテーブル partition
    )
    WHERE rk > 1                 -- 最初に登録したコピー以外
  ) d
  ON  t.dt IN (...)
  AND t.dt = d.dt AND t.DeviceId = d.DeviceId
  AND t.MessageID = d.MessageID AND t.registered_at = d.registered_at
  WHEN MATCHED THEN DELETE
  ```

  `DISTINCT` は、1 つのコピーが N 行あるために付ける。付けないと、本テーブルの 1 行に削除の指示の行が複数一致してエラーになる。
- **前回以降に書き込みがあったテーブル partition の求め方**:
  - snapshot の履歴をたどる。ジョブは、前回処理し終えた snapshot ID（しおり）を外部（DynamoDB、SSM Parameter Store など）に保存しておく。今回は、現在の snapshot から親の snapshot ID をたどってしおりまで戻り、その間の append の snapshot で追加されたデータファイルの partition を集める。
  - PyIceberg なら manifest を読むだけで、データは読まない。Spark なら差分読み取りでもよい。Athena の metadata テーブルからは正確に求められない。
  - コンパクション（replace）とジョブ自身の削除の snapshot は、新しい行を追加しないので飛ばす。append の snapshot が持つファイルの一覧は、後からコンパクションが走っても変わらないので、partition の特定はコンパクションの影響を受けない。
  - しおりは、削除が成功した後に更新する。重複の削除は冪等なので、しおりの更新に失敗しても、次の回が同じ範囲をやり直すだけで済む。
  - しおりに Iceberg のタグは使わない。S3 Tables では、利用者が作ったタグや branch が 1 つでもあると、テーブル全体の snapshot の管理が失敗する。
  - しおりにした snapshot は、snapshot の管理で消える（既定 最大 120 時間、最短 1 時間に設定できる）。ジョブはその期間内に追いつく必要がある。追いつけなかった場合は、対象期間のテーブル partition をすべて照合して復旧する。
  - 既存の Lambda の commit が多いと、1 回にたどる snapshot も多い（毎秒 5 commit なら 1 日 約 43 万）。ジョブは 5〜15 分ごとに実行する。
  - 遅れて届いた古いデータも、追加された回の対象に、その古いテーブル partition として入るので漏れない。遅延データが多くの古い partition に散らばる場合は、直近の partition は短い間隔で処理し、古い partition は一覧を記録しておいて 1 日 1 回まとめて処理する。
  - 同一テーブル partition 条件が成り立たない場合は、全体照合方式にする。新しく入った行のキーを、テーブル全体のキー列と照合する。費用は保持期間に比例して増える。
- **落とせる範囲**: 全期間。
- **本テーブルへの出方**: ジョブが実行されるまでの間は重複が見える。
- **前提・制約**:
  - 登録日時は、次のどちらかを満たす必要がある。どちらも満たさないと、残すコピーの行まで消してしまう。
    - コピー単位（バッチ単位かメッセージ単位）で、N 行に同じ値を入れる。上の SQL の例はこの場合。
    - 行ごとの値にする場合は、行識別子（2.4 節）を持つ。照合は行識別子まで含めた単位で行い（`PARTITION BY dt, DeviceId, MessageID, 行識別子`）、行ごとに最も早く登録された行を残す。残る行が別々のコピーのものになることがあるが、加工は決定的でコピーの中身は同じなので、結果は変わらない。
  - 同じメッセージの 2 つのコピーが同じバッチに入ると、登録日時も含めて全列が同じ行になり、どちらが先か決められない（producer の再送のように、同じ Kafka の partition に続けて届く重複で起きやすい）。Lambda のバッチ内重複排除で防ぐ。防げない場合は、そのキーだけ「全列が同じ行を 1 コピー分にまとめて入れ直す」を 1 回の MERGE で行う。
  - 消すコピーは、列の値（登録日時）で選ぶ。ファイルのパスで選ぶ方法は、コンパクションでファイルがまとめられると使えないので採らない。
  - 既存の Lambda はジョブの実行中も追記し続ける。既定の分離レベル（serializable）では、削除の commit は、読み込んだ snapshot 以降に対象のテーブル partition へファイルが追加されていると失敗するので、ほぼ毎回失敗する。テーブルの `write.delete.isolation-level` と `write.merge.isolation-level` を `snapshot` にする（Athena がこの設定に従うかは未確認）。snapshot にしても、削除はジョブが読んだ時点の行だけを対象にするので、後から追記された行は消えない。削除中に入った新しいコピーは、次の回が拾う。
  - Athena の削除は positional delete として書かれ、S3 Tables の compaction で物理的に消える。
  - Lambda は呼び出しごとに本テーブルへ commit するので、基準ケースの流量では commit 頻度の問題（4.1 節）がある。流量が少ない場合の案。
- **ジョブの実装とトリガー**:
  - EMR（Spark）: 1 つのジョブで、partition の特定（差分読み取り）から削除までを行える。EventBridge Scheduler から `StartJobRun` を直接呼び、EMR 側の同時実行数を 1 にする（5.2 節の Parquet 出力 + 定期 MERGE と同じ）。
  - PyIceberg + Athena: 小さなジョブ（コンテナか Lambda）が PyIceberg で partition を特定し、Athena の削除を組み立てて実行する。Step Functions か EKS の CronJob（`concurrencyPolicy: Forbid`）から実行する。
- **メリット**: 既存の処理をほぼそのまま残せる。状態ストアが不要。窓の制約がない。
- **デメリット**:
  - 重複が一時的に見える。
  - **Lambda の改修が要る**。登録日時の列を、バッチ単位（またはメッセージ単位）で入れる（2.2 節の前提。行ごとの値にするなら、行識別子も要る）。同じバッチに入ったコピーは登録日時で区別できないので、バッチ内重複排除も入れる。
  - ジョブの運用が必要（しおりの管理、snapshot の保持期間内に追いつくこと、分離レベルの設定）。
  - 全体照合方式では、費用が保持期間に比例して増える。
- **費用**:
  - 共通費用: 全案に共通の費用に加えて、commit の共通費用（約 1,200 ドル/月）がかかる。
  - 保存は全案に共通の費用に含めている。重複が多いほど増える。
  - ジョブの読み取り（Athena）: 削除の MERGE は、対象の partition のキー列と登録日時を 2 回読むと仮定する。
    - 1 日 1 回、日単位のテーブル partition: 1 日分（約 0.13TB）× 2 で **約 40 ドル/月**。
    - 15 分ごと（snapshot の履歴をたどる量を抑える場合）: 日単位のテーブル partition では毎回当日の partition（平均 約 65GB）を読むので **約 1,900 ドル/月**、時間単位なら **約 80 ドル/月**。
    - 全体照合方式: 1 か月保持で **約 1,200 ドル/月**、12 か月保持で **約 14,000 ドル/月**（1 日 1 回）。
  - snapshot の履歴をたどる metadata の GET は、15 分ごとでも約 10 ドル/月。
  - 削除が書く positional delete は、コンパクションで処理される（4.1 節のコンパクション費用に含める）。

#### 読み取り時の重複排除

- **仕組み**: メッセージ（`DeviceId + MessageID`）ごとに、1 つの書き込み ID の行だけを返す VIEW を作り、利用者は VIEW を読む。VIEW の重複除去（`ROW_NUMBER() OVER (PARTITION BY ...)`）には、`DeviceId`、`MessageID` に加えてテーブルの partition 列を入れる。
- **落とせる範囲**: 全期間（VIEW を経由した読み取りに限る）。
- **前提・制約**:
  - テーブルの partition 列を `PARTITION BY` に入れると、利用者のクエリの partition 列の条件が VIEW の内側まで押し下げられ、読む範囲がクエリの範囲だけになる見込み（Athena で押し下げられるかは要確認）。同一テーブル partition 条件が前提で、成り立たないと、別のテーブル partition にあるコピーは除かれない。
  - partition 列を入れない場合や、押し下げが効かない場合は、どのクエリも本テーブルの全期間を読む。
- **メリット**: 書き込み側を変えなくてよい。
- **デメリット**: 保存データには重複が残る。クエリのたびに重複除去の集約が走り、データ量に比例して費用と時間が増える。VIEW を経由しない読み取りには効かない。
- **費用**:
  - 共通費用: 全案に共通の費用に加えて、commit の共通費用（約 1,200 ドル/月）がかかる。
  - 押し下げが効く場合: 費用はクエリが読む範囲に比例する。1 か月分（圧縮後 約 8.6TB、1 回 約 43 ドル）を読むクエリが 1 日 1 回なら **約 1,300 ドル/月**、1 日 10 回なら **約 13,000 ドル/月**。1 日分（約 0.29TB、1 回 約 1.4 ドル）を読むクエリなら、1 日 10 回で **約 430 ドル/月**。
  - 押し下げが効かない場合: 毎回全期間を読む。1 か月保持なら上の 1 か月分と同じだが、12 か月保持では 1 回 約 520 ドルで、1 日 1 回でも **約 15,600 ドル/月** になる。

### 5.4 処理基盤を追加・変更する案

#### Kafka 内での重複排除（Lambda の前）

- **仕組み**: Kafka Streams か Flink のアプリが、zlib 解凍と protobuf デコードだけを行って `message_key` を取り出し、キーで Kafka の partition を振り直して重複を除き、元のバイト列を重複排除済みの topic に書く。Lambda はその topic を読む。
- **落とせる範囲**: state の TTL 内。
- **前提・制約**:
  - 加工は載せない（デコードのみ）。
  - 重複排除アプリ自身が重複を作らないよう、Kafka のトランザクション（exactly-once）を使う。
- **メリット**: Lambda はほぼ変更しなくてよい。キーで Kafka の partition を振り直すので、同じキーの判定が 1 か所に集まり、同時実行の問題が出ない。
- **デメリット**: デコードが二重になる。基盤（Streams / Flink、重複排除済みの topic）が増える。state の大きさは `流量 × TTL`。
- **費用**:
  - 共通費用: 全案に共通の費用に加えて、commit の共通費用（約 1,200 ドル/月）がかかる。
  - Flink（Managed Service for Apache Flink）: デコードだけなら計算は小さいが、24 時間分の state（約 216〜432GB）を持つ。KPU 1 つあたりのローカルストレージ 50GB に収めるには約 10 KPU が要る。約 11 KPU（アプリの管理分 1 を含む）× 0.142 ドル/時 × 720 時間と実行時ストレージで、**約 1,200 ドル/月**（推定）。
  - 重複排除済み topic（7 日保持、レプリカ 3）: EBS（gp3、約 18TB）が約 1,700 ドル/月、レプリケーションと読み書きの AZ 間転送が約 1,700 ドル/月で、**約 3,500 ドル/月**。ブローカーの CPU やネットワークの増強が必要なら、その分が加わる。
  - 合計（commit の共通費用を除く）: **約 4,700 ドル/月**。

#### 正規化 topic 経由の重複排除（Lambda の後）

- **仕組み**: Lambda は加工した結果を、`message_key` をキーにした正規化 topic に書く。Flink などが重複を除いて S3 Tables に書く。
  - 後段は Flink ではなく、2 段目の Lambda（ESM）でもよい。同じキーは正規化 topic の同じ Kafka の partition に入り、ESM は Kafka の partition ごとに 1 つの Lambda でしか処理しない。そのため、同じキーを 2 つの Lambda が同時に処理することがなくなり、状態ストアの予約方式や upsert の同時実行の問題が単純になる。Iceberg への commit 競合は残る。
- **落とせる範囲**: state で判定するなら TTL 内。Flink の Iceberg sink の upsert（equality delete）を使うなら全期間（unique keys に行識別子とテーブル partition の元になる列を含める必要があり、同一テーブル partition 条件が前提）。
- **メリット**: 加工は Lambda に残せる。重複排除の state と commit を Flink に任せられる。
- **デメリット**: Kafka の topic と Flink の運用が増え、経路が長くなる。equality delete を使う場合、PyIceberg で読めなくなる点は Firehose と同じ。
- **費用**:
  - 前段の Lambda は Kafka に書くだけになり、commit 待ちがないので、全案に共通の Lambda の費用が約 800 ドル/月下がる。
  - 正規化 topic（7 日保持、レプリカ 3）: Kafka 内での重複排除と同じく約 3,500 ドル/月。
  - 後段を Flink にする場合: state を持つ分で約 1,200 ドル/月（推定）。Iceberg への commit は checkpoint の間隔で決まるので、commit の共通費用はほぼかからない。合計 **約 4,700 ドル/月**。
  - 後段を Lambda にする場合: 2 段目の Lambda（加工なしで、主に commit 待ち）が約 900 ドル/月で、topic と合わせて **約 4,400 ドル/月**。これに commit の共通費用（約 1,200 ドル/月）と状態ストアの費用が加わる。

#### Flink で加工ごと処理

- **仕組み**: Lambda をやめ、Flink が Kafka から読んで、解凍、デコード、加工、重複排除、書き込みまでを行う。
- **落とせる範囲**: 重複排除の方式次第（state なら TTL 内、upsert なら全期間）。
- **前提・制約**: 加工を Flink で処理しきれるかが未検証。
- **メリット**: 処理が 1 か所にまとまる。checkpoint と連動した commit で、種別 1 の重複が出ない。
- **デメリット**: 加工の移植が必要。処理能力の検証が前提。
- **費用**:
  - Lambda と同じ処理量を Flink でこなすと仮定すると、加工に約 25〜30 vCPU が要る（毎秒 5 万件 × 0.5ms）。約 31 KPU × 0.142 ドル/時 × 720 時間で約 3,200 ドル/月、実行時ストレージ（KPU あたり 50GB、0.12 ドル/GB 月）が約 190 ドル/月で、**約 3,400 ドル/月**（推定）。
  - 全案に共通の Lambda の費用（約 3,000 ドル/月）と、commit の共通費用（約 1,200 ドル/月）は不要になる。
  - 重複排除の state を持つ場合は、その分の KPU（約 10 KPU、約 1,000 ドル/月）が加わる。

#### Kafka Connect Iceberg sink

- **仕組み**: Strimzi の KafkaConnect 上で Iceberg sink connector を動かす。解凍、デコード、加工は Converter / SMT として実装する。
- **落とせる範囲**: 未確定。sink は commit を一元化して種別 1 の重複を防ぐ。種別 3 を防ぐには upsert 機能が必要だが、Apache Iceberg 本体の connector で使えるかは未確認（Tabular 版には upsert の設定がある）。
- **前提・制約**: S3 Tables（REST catalog）に接続できるかは要確認。
- **メリット**: EKS 上の Strimzi と親和性が高い。commit をコネクタがまとめる。
- **デメリット**: 加工を Java で実装し直す必要がある。
- **費用**:
  - Strimzi の KafkaConnect を動かす EKS ノードが増える。加工の計算量は Lambda と同程度と見込み、約 30 vCPU 分として m7g.2xlarge（8 vCPU、0.4216 ドル/時）4 台に予備 1 台で、**約 1,500 ドル/月**（推定）。
  - 全案に共通の Lambda の費用（約 3,000 ドル/月）と、commit の共通費用は不要になる。commit はコネクタの commit 間隔で決まるので、PUT は少ない。
  - 重複排除に upsert を使う場合は、equality delete の分のコンパクションが加わる。

#### Spark Structured Streaming

- **仕組み**: Spark が Kafka から読んで解凍、デコード、加工を行い、`dropDuplicatesWithinWatermark` で窓内の重複を除くか、`foreachBatch` で本テーブルへ MERGE する。Glue のストリーミング ETL（Spark ベース）でも同じ構成にできる。
- **落とせる範囲**: `dropDuplicatesWithinWatermark` なら窓内、MERGE なら全期間。
- **前提・制約**: zlib 解凍は UDF で実装する想定（Python UDF はオーバーヘッドが大きい）。
- **メリット**: サンプル実装（kafka2/consumer）がある。MERGE を使えば全期間の重複を落とせる。
- **デメリット**: クラスタと state の運用が増える。加工の移植が必要。
- **費用**:
  - Glue のストリーミングジョブを常時動かす。加工に約 30 vCPU が要る見込みで、G.1X（1 DPU = 4 vCPU）を 9 DPU（ドライバーを含む）× 0.44 ドル/時 × 720 時間で、**約 2,900 ドル/月**（推定）。
  - 全案に共通の Lambda の費用（約 3,000 ドル/月）と、commit の共通費用は不要になる。commit はマイクロバッチごと（例: 1 分ごと）なので少ない。
  - `foreachBatch` で毎回 MERGE すると、本テーブルの読み取りがマイクロバッチの回数だけ発生するので、テーブル partition 限定で照合できることが前提になる。それでも毎回当日のテーブル partition を読む。1 分ごとのマイクロバッチでは、日単位のテーブル partition なら毎回平均 約 65GB、時間単位なら約 2.7GB のキー列を読むので、時間単位などの細かいテーブル partition にしないと重い（処理量は未検証）。

#### 圧縮バイトの着地 + バッチ ETL

- **仕組み**: Kafka のレコードを圧縮されたまま通常の S3 バケットに書き、定期的なバッチ（Glue / EMR）で解凍、デコード、加工、重複排除、MERGE を行う。
- **落とせる範囲**: 全期間。
- **メリット**: 重複を加工の前に落とせる。スケールアウトしやすい。
- **デメリット**: 原本を残す要件がないので、利点が小さい。反映がバッチ間隔で遅れる。ETL の運用が増える。
- **費用**:
  - 着地: Lambda が圧縮されたまま S3 に書くだけなら、Lambda は約 70 ドル/月、PUT は約 60 ドル/月。
  - 原本の保存: 1 日分（約 0.86TB）を S3 標準で保持して約 22 ドル/月（ETL の後に削除する前提）。
  - ETL の計算: 加工と重複排除を Glue で 1 日 1 回まとめて行う。加工の計算量を 1 日 約 600 vCPU 時間（150 DPU 時）として、**約 2,000 ドル/月**（推定）。
  - MERGE の読み取り: 上の MERGE 系の案と同じ（テーブル partition 限定で約 60 ドル/月、全体照合で 1 か月保持なら約 600 ドル/月、12 か月保持なら約 7,000 ドル/月）。
  - 合計: **約 2,200 ドル/月**（テーブル partition 限定）、**約 2,800 ドル/月**（全体照合、1 か月保持）、**約 9,200 ドル/月**（全体照合、12 か月保持）。全案に共通の Lambda の費用（約 3,000 ドル/月）と、commit の共通費用は不要になる。

### 5.5 補助の案

#### offset 冪等

- **仕組み**: Lambda が commit するとき、バッチの座標（Kafka の partition と最後の offset）を snapshot properties に記録する。再配信されたバッチは、記録済みの座標と照合して書き込みを省く。
- **落とせる範囲**: 種別 1 のみ。
- **前提・制約**:
  - すべての Kafka の partition の Lambda が同じテーブルに commit するので、自分の Kafka の partition の記録を探すには snapshot の履歴をさかのぼる必要がある。
  - 古い snapshot は S3 Tables の snapshot 管理で消える（CDK の既定は最大 120 時間）。
- **メリット**: 追加の部品が不要で、費用もほぼゼロ。
- **デメリット**: 種別 2・3 は防げない。commit が多いと、履歴の走査が重くなる。キーによる重複判定を入れれば種別 1 も防げるので、その場合は省略してよい。
- **費用**: 追加の PUT はない。snapshot の履歴をさかのぼるために、commit ごとに metadata の GET が増える。1 commit あたり 10 回と仮定すると、月 約 1.3 億 GET × 0.00037 ドル/1,000 件で **約 50 ドル/月**。

## 7. どの案でも必要な措置

- **バッチ内重複排除**を入れる。
- テーブルに **書き込み ID の列**（登録日時で代用できる。2.2 節）を持たせる（`DeviceId` と `MessageID` の列は既にある）。行識別子は、unique keys で upsert する案を選ぶ場合だけ追加する。
- テーブルの **partition 列は、payload の中のメッセージの生成時に決まる値**（計測時刻など）から作る。取り込み時刻などを使うと同一テーブル partition 条件が成り立たず、どの案でも照合範囲をテーブル partition で絞れなくなる。
- 読む側が差分を抽出できるよう、**MERGE の実行 ID（Lambda が本テーブルへ直接書く案では取り込み時刻）の列**を持たせる（8 章）。テーブルの partition 列にはしない。
- 1 バッチの行は **1 回の append commit**（Parquet 出力の案では 1 ファイル）で書く。Iceberg の commit も S3 のオブジェクト書き込みもアトミックなので、途中までの行が見える状態にはならない。
- Lambda が Iceberg に commit する案では、**commit 競合時の再試行**が必要。PyIceberg は PR #3320 を含む版から自動で再試行するが、append は競合を検証せずに載せ替える（10 章）。それより前の版では、Lambda に再試行を実装する。
- ESM で **`ReportBatchItemFailures`** を有効にし、失敗したレコードだけを返す。例外でバッチ全体を失敗させると、成功した分まで再配信されて重複の原因になる。
- **壊れたデータ**（解凍やデコードの失敗）は DLQ に隔離する。
- **解凍後のサイズに上限**を設ける（zlib 爆弾対策）。
- **`sort_order`** は、どの列でファイル単位の読み飛ばしを効かせるかで決める。`(DeviceId, MessageID)` にするとキーの照合で読み飛ばせるが、テーブル partition 限定の照合は partition 内の全行を読むので効果は小さい。読む側の差分抽出（8 章）を重視するなら、MERGE の実行 ID（または取り込み時刻）を先頭にする。どちらも S3 Tables の sort compaction の後のファイルにだけ効く（PyIceberg の append は書き込み時に並べ替えない見込み）。

## 8. 読み出し側の差分抽出

テーブル partition をデバイス内の時刻で切ると、遅れて届いたデータは過去の partition に入る。そのため、読む側は「当日の partition」ではなく、取り込み時の値を持つ列で新しい行を抽出する。

### 8.1 抽出の方法

| 観点 | 取り込み時の値の列（推奨） | snapshot の差分（Iceberg の incremental read） | row lineage（Iceberg v3） |
|---|---|---|---|
| 仕組み | MERGE の実行 ID（または取り込み時刻）の列で、前回より後の行を抽出する | 前回読んだ snapshot から今回の snapshot までに追加されたファイルを読む | 行ごとの `_last_updated_sequence_number` で、前回より後の commit の行を抽出する |
| 読むデータ | 列の統計が範囲に重なるファイル。コンパクション後は粗くなる | 追加されたファイルだけ | 取り込み時の値の列と同じ |
| 削除の反映 | される | されない | される |
| 抽出の遅れ | 定期 MERGE なら余裕は不要。Lambda が直接書く案では Lambda のタイムアウト分を空ける | 不要 | 不要 |
| エンジン | Athena で読める | Spark（Athena は不可、PyIceberg は未確認） | v3 のテーブルが必要。Athena は v3 を扱えない |

- **取り込み時の値の列**:
  - partition 列ではないので、同一テーブル partition 条件には影響しない。
  - テーブル全体は読まない。Iceberg はデータファイルごとに列の最小値と最大値を持つので、範囲に重ならないファイルを開かずに飛ばせる（Athena での効き方は未確認）。飛ばせるのは列の値がファイルごとに固まっている場合だけで、取り込み時の値は固まるが、キーは固まらない。
  - コンパクションが古い行と新しい行を同じファイルにまとめると、読み飛ばしが粗くなる。sort order の先頭にこの列を置けば緩和できる（7 章）。
  - metadata（現在の snapshot の manifest）は毎回すべて読む。量はテーブルのファイル数に比例する。
- **snapshot の差分**: 範囲内の append の snapshot で追加されたファイルを、そのまま返す。後から DELETE で消した行も返す（削除の情報を読まない）。DELETE や MERGE の snapshot は飛ばす。テーブルに重複を入れない案のうち、本テーブルへ append する案でしか使えない。読む側が止まっていた期間の snapshot を残す必要があり、commit 頻度が高いと metadata の読み取りも重い。
- **row lineage**: commit の順に正確に抽出でき、削除も反映される。ただし Athena が v3 に対応していないので、Athena で書く MERGE や読む側をすべて Spark に移す必要がある。

### 8.2 重複排除の方式との組み合わせ（取り込み時の値の列の場合）

| 重複排除の方式 | 列を付ける場所 | 抽出してよい範囲 |
|---|---|---|
| Parquet 出力 + 定期 MERGE、staging + 定期 MERGE | MERGE（実行ごとの ID か時刻） | 最後に終わった MERGE まで。MERGE は直列なので余裕は不要 |
| Parquet 出力 + 定期 MERGE（反映を `add_files` にする場合） | Lambda（ファイルを書き直さないので、登録時には付けられない） | 最後に終わったジョブの締め時刻 − Lambda のタイムアウトまで |
| 追記 + 定期重複排除ジョブ | Lambda | ジョブが処理し終えた範囲まで。ジョブは先着のコピーを残すので、一度読んだ行が後から消えることはない |
| 書き込み前に判定する案 | Lambda | 現在時刻 − Lambda のタイムアウトまで |

- **Lambda のタイムアウト分を空ける理由**: 複数の Lambda が同時に commit するので、取り込み時刻の順と commit の順が逆転する。先に読んだ範囲に、後から commit された行が入ると取りこぼす。commit は必ず Lambda の実行中に終わるので、タイムアウト分（と時計のずれの分の少しの余裕）を空ければ取りこぼさない。
- MERGE 系で Lambda の時刻を使うと、MERGE が過去の時刻の行を後から入れるので取りこぼす。列は MERGE の時点で付ける。
- 窓のある案では、窓を超えて漏れた重複はそのまま読まれる。

## 9. 進め方（推奨）

1. 7 章の措置を入れる。テーブルの partition はデバイス内の時刻の時間単位にする（モデルなどを加えてもよい）。
2. Lambda は加工した行を Parquet にして通常の S3 バケットに書くだけにし、Iceberg に commit しない（Parquet 出力 + 定期 MERGE）。
3. MERGE ジョブを 1 本だけ、1〜5 分ごとに実行する。照合はテーブル partition 列 + `DeviceId` + `MessageID` で行い、行に MERGE の実行 ID を付ける。エンジンはまず Athena にし、実際の流量での実行時間と読み取り量を測る。EKS で Spark を運用できるなら EMR on EKS でもよい。
4. 読む側は、MERGE の実行 ID で差分を抽出する（8 章）。
5. 遅れて届くデータが多くの時間帯に散らばるなら、直近のテーブル partition と古いテーブル partition で MERGE の経路を分ける。
6. MERGE が間隔内に終わらない場合は、ジョブの反映の方法を `add_files` に変える（データを書き直さないので速い）か、エンジンを EMR に変える。
7. 実際の流量が少なく、Lambda の commit が成り立つ場合は、追記 + 定期重複排除ジョブでもよい。重複が見える時間を短くする必要があれば、直近 K 件リング、Valkey の時間窓（TTL 1 時間）、共有 Bloom filter を書き込み前に加える。窓を超えた重複は定期ジョブが拾う。DynamoDB は、この流量では費用の桁が合わない。
8. 本テーブルへの反映を秒単位にしたい場合は、Iceberg 自体が向いていない。リアルタイムの経路を別のストアに分けて検討する。
9. Firehose への upsert 書き込みは、流量が 1 テーブルあたりの上限（東京などでは 1 MiB/秒）に収まる場合だけ検討する。

## 10. 確認済みの技術情報

- **Lambda ESM**
  - event source mapping は at-least-once で、重複処理が起こり得る。（[Lambda Developer Guide](https://docs.aws.amazon.com/lambda/latest/dg/invocation-eventsourcemapping.html)）
  - Kafka でも `ReportBatchItemFailures` で、失敗したレコードの Kafka の `partition` と `offset` だけを返せる。空の応答はバッチ全体の成功とみなされる。（[Kafka のエラー処理](https://docs.aws.amazon.com/lambda/latest/dg/kafka-retry-configurations.html)）
  - batch size の上限は 10,000 件で、payload は同期呼び出しの上限（6MB）まで。（[Lambda API](https://docs.aws.amazon.com/aws-sdk-php/v3/api/api-lambda-2015-03-31.html)）
  - Kafka の partition 内の順序を保つため、poller 数は Kafka の partition 数が上限。（[AWS Big Data Blog](https://aws.amazon.com/blogs/big-data/building-serverless-event-streaming-applications-with-amazon-msk-and-aws-lambda/)）
- **S3 Tables**
  - binpack compaction は、小さいファイルの統合と同時に pending deletes を適用する。`sort_order` を定義すると sort compaction になる。（[S3 Tables のメンテナンス](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-maintenance.html)）
  - compaction は equality delete も適用するが、Intelligent-Tiering の IA / AIA 層にあるファイルは compaction しない。（[AWS Storage Blog](https://aws.amazon.com/blogs/storage/optimize-data-management-on-s3-tables-with-intelligent-tiering/)）
  - 未参照ファイルの削除は既定で、参照されなくなって 3 日後に noncurrent、さらに 10 日後に削除する。（[テーブルバケットのメンテナンス](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-table-buckets-maintenance.html)）
  - snapshot の保持は既定で最小 1 個、最大 120 時間。（[CDK の Table](https://docs.aws.amazon.com/cdk/api/v2/docs/@aws-cdk_aws-s3tables-alpha.Table.html)）
  - snapshot の保持期間（maxSnapshotAgeHours）の最小値は 1 時間。利用者が作ったタグや branch が 1 つでもあると、テーブル全体の snapshot の管理が失敗する。（[テーブルのメンテナンス](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-maintenance.html)、[メンテナンスの考慮事項](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-considerations.html)）
  - テーブルの場所で使えるオブジェクトの API は、PutObject、GetObject、HeadObject と multipart の操作。ListObjects はない。（[S3 Tables のオブジェクト API](https://docs.aws.amazon.com/AmazonS3/latest/API/developing-s3-tables-APIs.html)）
  - 未参照ファイルの削除の設定はテーブルバケット単位で、バケット内の全テーブルに適用される。noncurrent になったオブジェクトを戻すには AWS サポートへの依頼が必要で、削除後は戻せない。（[テーブルバケットのメンテナンス](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-table-buckets-maintenance.html)）
  - 料金は、ストレージ、リクエスト、オブジェクト監視（保存しているオブジェクトの数）、コンパクション（処理したオブジェクトの数とバイト数）、レプリケーション。テーブルバケット自体は無料。snapshot の管理と未参照ファイルの削除の料金は、料金ページに記載がない。（[S3 の料金](https://aws.amazon.com/s3/pricing/)）
  - Intelligent-Tiering を使える。30 日アクセスがないと Infrequent Access 層（40% 安い）、90 日で Archive Instant Access 層（さらに 68% 安い）に移る。コンパクションなどのメンテナンスでは層は戻らない。（[What's New](https://aws.amazon.com/about-aws/whats-new/2025/12/s3-tables-intelligent-tiering-storage-class/)）
- **単価**
  - 4.1 節の単価は、AWS の Price List（公開ファイル `https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/<サービス>/current/ap-northeast-1/index.json` と Price List API）から 2026-10-28 に取得した東京リージョンの値。
- **Athena**
  - `UPDATE / MERGE INTO / DELETE` は、table property に関係なく merge-on-read で動作する。（[Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/apache-iceberg-on-aws/iceberg-athena.html)）

  - Direct PUT の stream ごとの上限は、バージニア北部・オレゴン・アイルランドで 500,000 件/秒・2,000 リクエスト/秒・5 MiB/秒、その他のリージョンで 100,000 件/秒・1,000 リクエスト/秒・1 MiB/秒。（[Firehose の quota](https://docs.aws.amazon.com/firehose/latest/dev/limits.html)）
